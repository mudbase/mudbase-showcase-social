# Build Plan — Mudbase Showcase: Social (Flutter)
Generated: 2026-07-31
Mode: port (Flutter reimplementation of the Next.js reference app in `../web`)
Type: mobile (fullstack via BaaS, no custom backend)
Stack: Flutter + Dart, Riverpod (plain `Notifier`/`AsyncNotifier`, no codegen), go_router,
`flutter_secure_storage`, `socket_io_client`, talking directly to `cloud.mudbase.dev` through the
real, generated Mudbase Dart SDK (`mudbase_sdk`).

## Stack Decisions
- Mirrors `../mobile-flutter`-sibling architecture from `mudbase-showcase-ecommerce`
  (verified by reading that project's `lib/core/*`, `lib/features/auth/auth_controller.dart`,
  `lib/router/app_router.dart`, `lib/theme/app_theme.dart` before writing a line of this app) —
  same `AuthService`/`MudbaseDataService` raw-`dio` pattern, same `SecureTokenStorage`, same
  `AsyncNotifier`-based `AuthController` with `callAuthorized`/401-refresh-retry, same plain
  Riverpod (no `riverpod_generator`/`freezed`) for the same reason: no Flutter SDK is installed in
  this build environment, so nothing generated by `build_runner` could be iteratively verified
  locally — every provider and model here is written to be verifiable by `dart analyze` alone.
- **New relative to the ecommerce port: realtime.** The ecommerce Flutter app explicitly opted out
  of Socket.IO ("brief didn't call for realtime specifically for the mobile version"). This app's
  brief does call for it (`FeedScreen` live updates), so `socket_io_client` is added and
  `lib/core/mudbase_socket_service.dart` ports the web app's `src/lib/mudbase-socket.ts` /
  `src/hooks/usePostsLive.ts` contract (`subscribe:collection` → `db:create`/`db:update`) to Dart.
- No custom backend of any kind, same as the web app and the ecommerce port: every persistence,
  auth, and realtime concern is a Mudbase REST/WebSocket call made directly from the device.
- Sign-in required before browsing (same deliberate simplification the ecommerce Flutter port
  documents and this task's brief allows) - no anonymous-guest bootstrap, unlike the web app. This
  sidesteps the web app's silent-anonymous-session dance entirely; every screen sits behind
  `AuthController`.

## Auth Flow
```
Register   → POST /api/auth/local/signup/customer (agreedToTerms: true required)
                                        → 201, no token, requireVerification: true
Verify     → user clicks the emailed link (out of app - no deep-link handler in this pass,
             same as the web app has no in-app resend) → email verified server-side
Login      → POST /api/auth/local/login → 403 EMAIL_VERIFICATION_REQUIRED until verified
                                        → 200 + token/refreshToken once verified
Refresh    → POST /api/auth/refresh (single-use rotating refresh token; AuthController dedupes
             concurrent refreshes via `_refreshInFlight`, mirrors the ecommerce port exactly)
Logout     → POST /api/auth/logout (best-effort revoke; local session always cleared regardless)
```
Unlike the web app, this app requires sign-in before browsing at all (see "Stack Decisions") - no
anonymous session bootstrap, so there is no guest-read path to port.

## Realtime
`FeedScreen` subscribes to the `posts` collection's Socket.IO room on entry:
`MudbaseSocketService.connect(token)` → `subscribe:collection {projectId, collectionId}` →
`db:create` (prepend, deduped by `_id` against the composer's own optimistic insert) / `db:update`
(patch whichever cached copy exists - the feed list or an open post-detail screen), exact same
contract as `web/src/hooks/usePostsLive.ts`, confirmed live in this session (see above). Connection
is torn down on logout (mirrors the web app's `useAuth.logout` disconnecting the socket so a stale,
now-invalid session token doesn't stay connected).

## UI Screens
- `/login`, `/register` — email+password; register shows a "check your inbox" message rather than
  assuming a session (mirrors the web app's verification-gate finding).
- `/feed` — `PostComposer` (text + optional image URL) + paginated `FeedList` (`page`/`limit`,
  "Load more"), live via `MudbaseSocketService`, pull-to-refresh.
- `/feed/post/:id` — post detail: full post, like toggle, `CommentList` (oldest-first),
  `CommentComposer`.
- `/profile/:userId` — resolved display name (best-effort, same denormalized-name strategy as the
  web app - see "Known limitations"), follower/following/post counts, that user's posts,
  follow/unfollow button (hidden on your own profile).
- `/account` — the signed-in user's own profile shortcut + sign out.

## Security Implementation
- Input validation: composer/comment forms cap length client-side (content 500 chars, comments 300
  chars, matching the web app) and require non-empty content before the create call fires.
- Authentication: Mudbase-issued JWT (access + refresh) held in `flutter_secure_storage`
  (Keychain/EncryptedSharedPreferences) - never `SharedPreferences` (hard project security rule,
  same as the ecommerce port), with 401 → refresh → retry handled once via
  `AuthController.callAuthorized`, deduped across concurrent calls (`_refreshInFlight`).
- Authorization: enforced server-side by Mudbase collection permissions (customer-only
  create/update, and every read in this app requires a real signed-in session since there is no
  anonymous bootstrap) - this app's own auth gate (the router redirect) is UX, not the security
  boundary.
- Secrets: none. Every `--dart-define` value (project ID, four collection IDs, base URL) is public,
  exactly like the web app's `NEXT_PUBLIC_*` vars and the ecommerce Flutter port's `EnvConfig` -
  there is no server-side credential anywhere in this app.

## Known Limitations (real platform constraints, not bugs - consistent with the web app's findings)

**Post images are a pasted URL, not an upload.** Confirmed live this session: `GET
.../buckets` returns `buckets: []` (no bucket exists to upload into), and independently, the web
app's build-plan already confirmed `rbacCheck("file","create")` only allows org-level
owner/admin/developer - no project end-user JWT, including a real verified `customer`, can ever
pass it. `PostComposerSheet` uses a plain `imageUrl` text field.

**No `users` collection - profile display names are best-effort**, same denormalization strategy
as the web app's `useResolvedDisplayName`: most recent post's `authorName`, falling back to a
`followingName` recorded by someone who follows them, falling back to the literal string "Member".

**No in-app email-verification resend or deep-link completion.** Same real constraint as the web
app - `resendVerificationEmail` requires a JWT an unverified account cannot obtain. This app does
not attempt an in-app "tap the link" deep-link handler either (out of scope for this pass); the
verification flow completes in whatever app opens the emailed link, same as the web app's own
`/verify-email` page would if opened from a mobile mail client.

**Like/follow uniqueness is check-then-act, not a compound unique index** (there isn't one on
these collection types) - reasonable for a demo, not airtight, and a real duplicate follow row from
an earlier concurrent session was observed live during this build's own verification (see finding
#7 above), which is direct evidence the caveat is real, not theoretical.

## Testing Note (environment constraint, same as the ecommerce Flutter port)
No Flutter SDK is installed in this build environment (`flutter` is not on `PATH`; only the Dart
SDK is) - confirmed before writing any code, same constraint the ecommerce port's README documents.
`flutter pub get`/`flutter analyze`/`flutter test` cannot be executed here because
`pubspec.yaml`'s `flutter: sdk: flutter` dependency cannot resolve without the Flutter SDK present
(verified directly: `dart pub get` against a probe pubspec with that dependency fails with "the
Flutter SDK is not available", both for this app's own `pubspec.yaml` and for a standalone probe).

What was actually, genuinely run in this environment rather than just written:

   every `lib/models/*`, every `lib/data/repositories/*`, `lib/config/env_config.dart`,
   `tool/manual_test.dart`) - done by copying them into a scratch package with a `flutter`-free
   `pubspec.yaml` (real deps only: `dio`, `mudbase_sdk` via the same path dependency, `built_value`,
   `socket_io_client`). **Zero issues found.** The two Flutter-only files this excludes
   (`secure_token_storage.dart`'s `flutter_secure_storage` import, and everything under
   `lib/features/`/`lib/widgets/`/`lib/router/`/`lib/theme/`/`app.dart`/`main.dart`) were written
   by hand against APIs confirmed from the real, pub-cache-resolved source of
   `flutter_riverpod`'s pure-Dart core (`package:riverpod`, same version) and `socket_io_client`
   2.0.3+1's real source (both fetched into the local pub cache and read directly, not guessed) -
